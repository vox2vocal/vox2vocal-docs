## 브리프 요약 (Brief Summary)

이 브리프는 Vox2Vocal P0의 첫 PRD 후보인 개인 계정 및 권한 PRD를 작성하기 위한 준비 문서다.

목표는 단일 개인 사용자가 앱과 관리자 페이지를 분리된 경험으로 사용하되, 일반 사용자 계정과 별도 관리자 계정을 통해 안전하게 접근하도록 만드는 것이다. 이 PRD는 곡 업로드, 음성 입력, preview 생성 자체를 정의하지 않고, 그 기능들이 의존하는 계정, 세션, 권한, 접근 차단, 기본 감사 기준을 잠근다.

## 대상 사용자 (Target Users)

- 개인 계정 소유자 (Personal Account Owner): 앱 계정을 생성하고 모든 개인 데이터의 소유자가 되는 단일 사용자.
- 앱 사용자 (App User): 앱에서 곡/구간 선택, 본인 음성 입력, preview 재생, self-voice 평가를 수행하는 사용자.
- 관리자 계정 사용자 (Admin Account User): 같은 개인이지만 관리자 페이지에서 곡 업로드, metadata 관리, 구간 정의, 권리/출처 메모를 수행하는 사용자.
- 실험 운영자 (Experiment Operator): 같은 개인이지만 job 상태, 실패, 삭제, 접근 로그를 확인하는 운영 범위의 사용자.

현재 대상이 아닌 사용자는 외부 학습자, 강사, 교육기관 운영자, 다중 사용자 팀, 제3자 관리자다.

## 문제 (Problem)

Vox2Vocal은 음원, 본인 음성, preview 산출물, pitch/note/발성 분석 결과를 다루기 때문에 계정과 권한 경계가 모호하면 P0 전체가 위험해진다.

특히 다음 문제가 있다.

- 앱과 관리자 페이지가 분리되어야 하지만, 같은 개인이 두 경험을 모두 사용할 수 있어야 한다.
- 일반 사용자 계정으로 관리자 페이지에 접근하면 곡 metadata, 권리 상태, 운영 기능을 잘못 변경할 수 있다.
- 관리자 계정은 앱 접근이 가능해야 하지만, 그 권한이 외부 공유, 다운로드, public URL, 수익화 허용으로 오해되면 안 된다.
- 처리 job, playback, 삭제, 권리/출처 변경 같은 민감 이벤트는 나중에 원인을 추적할 수 있어야 한다.
- 개인정보와 알림 연락처는 인증, 보안, 처리 상태 안내, 개인 알림 목적으로만 제한되어야 한다.

## 결정된 기준 (Resolved Decisions)

- 계정 생성 우선순위는 이메일/비밀번호, passkey, 소셜 로그인 순서로 둔다.
- 단, 사용 인증 provider 또는 기술 선택상 소셜 로그인이 선행되어야 한다면 소셜 로그인을 먼저 개발할 수 있다.
- 관리자 권한은 같은 계정의 `admin` role이 아니라 **별도 관리자 계정**으로 분리한다.
- 계정 삭제 요청 후에는 로그인, playback, job 생성, 관리자 접근을 모두 즉시 차단한다.
- 관리자 접근 실패와 권한 차단은 사용자에게 짧고 일반적인 메시지만 노출하고, 상세 사유는 감사 로그에 남긴다.
- push token은 계정 PRD에 최소 등록/해제 기준만 포함하고, 알림 템플릿, 발송, retry, in-app inbox 등 상세 알림 기능은 별도 알림 PRD로 분리한다.

## 목표 (Goal)

개인 계정 및 권한 PRD의 목표는 P0 MVP가 시작되기 전에 다음 기준을 명확히 하는 것이다.

- 단일 개인 사용자의 일반 앱 계정과 별도 관리자 계정 생성, 로그인, 세션, 계정 상태 기준을 정의한다.
- 일반 사용자 계정과 관리자 계정의 접근 범위를 분리한다.
- 일반 사용자 계정은 관리자 페이지에 접근할 수 없고, 관리자 계정은 앱 사용자 권한을 포함해 앱에 접근할 수 있게 한다.
- 앱, 관리자 페이지, 운영 범위, 시스템 처리 권한, 알림 권한을 구분한다.
- 외부 공유, 다운로드, public URL 생성, 목적 외 export, 모델 학습 사용은 권한으로도 허용되지 않게 한다.
- 계정/세션/권한 변경과 주요 차단 이벤트를 감사 가능한 형태로 기록한다.
- 이후 곡 업로드, 음성 입력, preview, 삭제/보관 PRD가 참조할 계정 경계를 제공한다.

## 성공 기준 (Success Criteria)

- 개인 사용자가 앱 계정을 생성하고 로그인할 수 있다.
- 계정 생성 우선순위는 이메일/비밀번호를 P0 기본으로 삼고, passkey와 소셜 로그인은 후속 또는 기술 의존성에 따라 확장할 수 있다.
- 일반 사용자 계정은 앱 기능에 접근할 수 있지만 관리자 페이지 접근은 차단된다.
- 관리자 계정은 관리자 페이지와 앱 모두에 접근할 수 있다.
- 권한이 없는 접근 시 관리자 기능, 곡 metadata 변경, 권리 상태 변경, 운영 job 조작이 차단된다.
- 계정 삭제 또는 비활성화 상태에서는 로그인, 앱, 관리자 페이지, playback, job 생성, 처리 요청이 모두 즉시 차단된다.
- 로그인, 로그아웃, 세션 만료, 관리자 접근 시도, 권한 차단, 계정 비활성화, token 폐기 이벤트가 감사 로그로 남는다.
- 권한 차단의 사용자 노출은 짧고 일반적인 메시지로 제한하고, 상세 reason code는 감사 로그에 남긴다.
- push token은 계정 PRD에서 등록/해제 lifecycle만 정의하고, 민감한 곡명, 권리 정보, 음성 내용을 payload에 포함하지 않는다.
- 이 PRD만으로 곡 업로드/구간 관리 PRD와 앱 입력 PRD가 참조할 actor, session, permission 기준을 알 수 있다.

## 제약 조건 (Constraints)

- 사용자는 한 명이며 다중 사용자, 강사/교육생, 팀/조직 권한은 범위 밖이다.
- 앱과 관리자 페이지는 완성형에서도 분리된 경험으로 유지한다.
- 개인 비상업 실험 시스템이며 수익화, 배포, 외부 공유, 공개 URL은 허용하지 않는다.
- 계정 정보와 연락처는 인증, 보안, 처리 상태 안내, 개인 알림 목적에 한정한다.
- 개인정보/보관/삭제의 상세 정본은 별도 `Privacy & Data Retention Policy`가 관리한다.
- 관리자 권한은 곡 업로드와 운영을 가능하게 하지만, 권리 확보 상태를 의미하지 않는다.
- P0에서는 정교한 조직 RBAC나 다중 tenant 권한 모델을 만들지 않는다.
- P0에서는 상세 알림 기능을 계정 PRD에 포함하지 않고, push token 등록/해제와 권한 상태만 계정 PRD에서 다룬다.
- 기술 구현 방식, API contract, DB schema는 이 브리프에서 확정하지 않는다.

## 확인된 사실 (Known Facts)

- 제품 대상은 프로젝트 소유자 본인인 단일 개인 사용자다.
- 앱과 관리자 페이지는 분리된 경험으로 유지한다.
- 일반 사용자 계정은 관리자 페이지에 접근할 수 없다.
- 관리자 권한은 별도 관리자 계정으로 분리한다.
- 관리자 계정은 앱 사용자 권한을 포함해 앱에 접근할 수 있다.
- 계정 생성 우선순위는 이메일/비밀번호, passkey, 소셜 로그인 순서다.
- 계정 삭제 요청 후에는 로그인, playback, job 생성, 관리자 접근을 모두 즉시 차단한다.
- 권한 차단 상세 사유는 사용자에게 노출하지 않고 감사 로그에 남긴다.
- 업로드 곡의 기본 권리 상태는 `rights_not_cleared_personal_use_only`다.
- preview와 관련 데이터는 외부 공유, 다운로드, public URL 없이 계정 내부에서만 접근되어야 한다.
- push 알림은 최소 payload로 처리 완료, 실패, 삭제, 보안 상태를 안내하는 용도다.
- 활성 DB 개인정보는 삭제 요청 후 7일 이내 삭제 또는 익명화하고, 백업은 최대 35일 rolling retention을 따른다.
- P0 MVP에는 계정/권한, 관리자 곡 업로드, 앱 입력, preview, self-voice 평가, 기본 audit이 포함된다.

## 가정 (Assumptions)

- 단일 개인 사용자는 일반 앱 계정과 별도 관리자 계정을 모두 소유할 수 있다.
- P0에서는 일반 사용자 계정과 관리자 계정을 물리적으로 분리하고, 두 계정이 같은 개인에게 귀속된다는 운영 전제를 둔다.
- 관리자 권한 부여는 수동 또는 seed 기반으로 시작해도 P0 검증에는 충분하다.
- 계정 삭제는 즉시 비활성화와 token 폐기를 우선하고, 저장 데이터 삭제는 후속 정책/운영 문서의 절차를 따른다.
- passkey와 소셜 로그인은 P0 이후 확장으로 두되, 인증 provider 선택상 소셜 로그인이 선행되어야 하면 순서를 조정할 수 있다.

## 리스크 (Risks)

- 계정/권한 PRD가 곡 업로드, 알림, 삭제 정책까지 과도하게 포함하면 P0 PRD 범위가 커질 수 있다.
- 별도 관리자 계정은 P0 구현과 운영이 조금 번거롭지만, 관리자 작업과 앱 사용자 작업의 감사 경계를 선명하게 만든다.
- 관리자 계정이 앱 접근 가능하다는 규칙이 외부 공유나 다운로드 허용으로 잘못 해석될 수 있다.
- 단일 사용자 전제에 너무 맞추면 이후 제품화 시 권한 모델을 재설계해야 할 수 있다.
- 삭제/비활성화/token 폐기 경계가 모호하면 삭제 요청 후에도 playback이나 job 생성이 가능해질 수 있다.
- 감사 로그에 민감정보를 직접 남기면 개인정보와 권리 정보 노출 위험이 생긴다.

## PRD 작성 전 질문 (Questions Before PRD)

핵심 정책 질문은 결정되었다. PRD 작성 전에는 다음 구현 범위 질문만 확인하면 된다.

1. P0 이메일/비밀번호 가입에서 이메일 인증을 필수로 둘 것인가, 아니면 개인 시스템이므로 수동 활성화로 시작할 것인가?
2. 별도 관리자 계정은 seed/admin script로 생성할 것인가, 제한된 관리자 가입 화면을 둘 것인가?
3. 계정 삭제 요청 후 사용자에게 보여줄 최소 상태 화면을 둘 것인가, 아니면 즉시 모든 UI 접근을 차단할 것인가?
